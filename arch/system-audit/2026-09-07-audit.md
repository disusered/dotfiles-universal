# System audit: 7 September 2026

## Applied and verified

- Relocated approximately 8.9 GiB of Pacman cache from root to
  `/home/system-cache/pacman/pkg`. Root changed from 90% used with 6 GiB available
  to 74% used with 15 GiB available; `/home` has about 180 GiB available.
  All partitions remain unchanged on the same physical SSD.
- Checksum verification passed before removing the original cache files.
  Pacman download-user directory access, retention dry runs, and access through
  the cleanup service's home-filesystem sandbox passed. The cleanup timer is active.
- Dell S3422DWG serial G1C4KK3 uses a description-based 144 Hz rule that follows
  it across DP connectors. The current DP-2 connection reports 143.975 Hz at
  3440x1440, position 0x0, scale 1; Hyprland reports no configuration errors.
  Physical reconnection and suspend/resume have not been tested.
- RomM and its database are now on demand and stopped. Their generated services
  have no default-target dependency. All three named data volumes remain.
  Start with `systemctl --user start romm.service`; stop both with
  `systemctl --user stop romm.service romm-db.service`.
- Minute resource and daily storage timers are active. Both first collectors
  exited successfully and wrote private JSONL files under
  `~/.local/state/system-audit`. See [monitoring instructions](README.md).

## Memory findings

Early after boot, the host had about 23 GiB available memory, no swap usage, and
no memory pressure. This cannot rule out growth during a full working day.

RomM's Valkey instance used about 618 MiB for data and 701 MiB RSS, with a
fragmentation ratio of 1.13. Six non-expiring LaunchBox metadata hashes account
for about 591 MiB. RomM documents downloading the full LaunchBox metadata
database locally: [metadata providers](https://docs.romm.app/latest/getting-started/metadata-providers/).
The observed footprint is explained; it is not a confirmed leak.

Valkey has no configured memory cap (`maxmemory=0`), with `noeviction`, RDB
snapshots enabled, last save successful, and AOF disabled. It also supports
background queues, so arbitrary eviction was not introduced. Running RomM on
demand avoids its idle footprint while preserving its data and providers.

boot ID, and service invocation changes. Compare seven daily storage samples
before claiming unbounded growth. Inaccessible storage is reported as incomplete
with a lower-bound total when available; no permissions were broadened.

and Skyrim launch behavior were preserved. No development caches, container
volumes, installed SDKs, or active-game shader caches were deleted.
